PHASE 12 -- ADVISORY RECOMMENDATION ENGINE
====================================================================================================
PRE-FLIGHT CHECK: locked pipeline reproduced 5,817 test blocks, Delhi P50 at the known
season peak = 7,795.2 MW -- identical to Phase 7-11. Nothing about
the demand model, stress score, or DISCOM ratios changes in this phase.

====================================================================================================
## 1. Recommendation rules
====================================================================================================
  Condition                                                     Category                    Advisory
----------------------------------------------------------------------------------------------------
  peak_risk in {HIGH, CRITICAL} AND hours_to_peak <= 2          DEMAND RESPONSE             Consider peak-period demand-response measures for the next few hours.
  peak_risk in {HIGH, CRITICAL} AND hours_to_peak > 2           PREPARE                     Prepare additional reserve/capacity ahead of the forecast peak.
  peak_risk == MODERATE                                         MONITOR                     Increase monitoring attention ahead of the forecast peak.
  peak_risk == LOW                                              MONITOR (routine)           No immediate action beyond routine monitoring.
  reliability == LOW                                            DATA QUALITY WARNING        Treat this forecast as low-confidence and prioritize confirmation of critical telemetry.
  reliability == MEDIUM                                         DATA QUALITY WARNING (lighter)Treat this forecast with moderate caution; some inputs were reconstructed or incomplete.
  util50 < 0.88 AND util90 >= 0.88                              PREPARE                     Prepare for the upper-demand scenario rather than relying only on the central forecast.
  max DISCOM relative_stress_p50 >= 0.90                        MONITOR                     Increase monitoring attention on {stressed_discom} (modeled relative stress {stressed_pct:.0f}% of its own 2025 reference) -- separately from {largest_discom}, which carries the largest modeled MW contribution ({largest_pct:.0f}%).
  stress_level in {HIGH, CRITICAL}                              CONSERVATION ADVISORY       Issue a public conservation advisory encouraging reduced non-essential demand during the forecast peak window.
----------------------------------------------------------------------------------------------------
  Every advisory text above is a TEMPLATE; every {field} is substituted from an actual backend
  value at evaluation time (Section 5/7 below) -- never freeform text, never an LLM call.
  Vocabulary used throughout: consider / prepare / monitor / evaluate / investigate / issue
  advisory. Never: execute / disconnect / shut down / reroute / switch a feeder.

====================================================================================================
## 2. Reliability-aware logic
====================================================================================================
  Reliability never claims the forecast IS wrong -- only that it is LESS TRUSTWORTHY, and says
  why, using the exact same reliability_reasons text produced by the locked Phase 7 rules. LOW
  reliability always produces a DATA QUALITY WARNING; MEDIUM produces a lighter version; HIGH
  produces none -- silence is meaningful here, not an omission.

====================================================================================================
## 3. Uncertainty-aware logic
====================================================================================================
  The rule 'P50 comfortable, P90 not' is the direct, disclosed callback to the exact finding
  that triggered Phase 8 (12 June: P50 86.6%, P90 93.5% of assumed capacity) -- this is now an
  explicit, reusable trigger rather than something only visible in a retrospective report.

====================================================================================================
## 4. DISCOM-aware logic
====================================================================================================
  The engine NEVER says 'X is the most stressed utility' as a bare claim. It always states
  contribution and relative stress as two separate, separately-sourced numbers, and names which
  utility each belongs to -- exactly preserving the Phase 11 finding that these can differ.
  If no utility's relative stress reaches 90% of its own reference, NO DISCOM advisory fires --
  quiet days stay quiet.

## 8. Limitations
====================================================================================================
  - This project's forecast is issued ONCE, 24h ahead, and is never refreshed closer to real
    time. The 'hours_to_peak' proximity trigger is genuine arithmetic, but it is demonstrated
    here at a manually chosen 'now' checkpoint (2h before peak) using the SAME static forecast,
    not a live-updating one. An operational version would need a forecast that re-issues through
    the day, which does not exist in this project.
  - Neither DEMAND RESPONSE nor CONSERVATION ADVISORY fired on any real test day (Section 5/6):
    peak_risk never reached HIGH/CRITICAL in this 61-day test period, so the proximity split
    (PREPARE at 24h vs DEMAND RESPONSE at 2h) could only be demonstrated on the labeled Phase 10
    What-If '+5C' input above, not on real history -- disclosed rather than glossed over.
  - The rule thresholds (2h proximity, 90% DISCOM relative-stress, the peak-risk/stress-level
    bands themselves) are judgment calls, consistent with earlier phases' documented bands, not
    independently validated against real operator decisions or outcomes.
  - DISCOM advisories inherit every limitation disclosed in Phase 11 -- BRPL/BYPL modeled from a
    same-day source, TPDDL from a single differently-dated source, NDMC/MES not modeled
    individually at all.
  - The CONSERVATION ADVISORY and DEMAND RESPONSE rules never fired on real historical test data
    (Section 6) -- their correctness rests on the What-If demonstration above, not on a real
    historical activation.
  - This is a rule table over the SAME single forecast used throughout the project; it does not
    reason about anything the forecast itself cannot see (fuel supply, generator outages,
    transmission constraints) -- it is strictly downstream of the demand-side model.

====================================================================================================
## 9. Recommendation
====================================================================================================
  CORE PRODUCT FEATURE. It is the first layer that turns every earlier phase's output (P50/P90,
  reliability, stress, risk, DISCOM allocation) into something a non-technical operator could act
  on without reading a report -- and it does so without ever exceeding what the underlying data
  supports: every advisory traces to a real backend field, uses advisory (not command) language,
  and stays silent on ordinary days (Section 6: most test days resolve to routine monitoring).
  It should NOT be simplified further -- the reliability-aware and DISCOM contribution-vs-stress
  distinctions are exactly the nuance this project has spent multiple phases establishing, and
  collapsing them into a single generic 'risk: high/low' would throw that away.
