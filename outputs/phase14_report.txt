6. 3-MINUTE TECHNICAL BACKUP EXPLANATION
============================================================================================
"The pipeline starts with two years of 15-minute Delhi load data plus hourly weather, resampled
to a common 15-minute grid.

DATA & PREPROCESSING: Two real data problems had to be solved before any modeling. First, there
are genuine telemetry gaps in the load series -- some blocks and even whole stretches are
missing. Our first imputation approach (simple same-time-yesterday filling) produced a
5,817-block full-test-period MAPE of about 6.01%; switching to nearest-observed-day imputation
-- filling a gap from the closest day that actually has real data for that time-of-day, rather
than a fixed lag -- improved that to 5.94%, and that is the version that's locked into the
system today. Second, every imputed block is flagged, and those flags feed directly into the
reliability score you saw in the demo -- a forecast built on more reconstructed data is
explicitly marked less trustworthy, not silently treated the same as one built on clean
telemetry.

GENUINE 24-HOUR-AHEAD FORECASTING: This is the part we were most careful about. Every feature
used to predict a given 15-minute block -- lagged demand, weather, calendar features -- is
constructed using only information available strictly 24 hours or more before that block, via
explicit time-shifted (shift-by-H) feature construction at the point the whole feature matrix is
built. That's enforced structurally, once, for every downstream use of the model -- Overview,
What-If, and Proof Mode all read from the same leakage-safe feature set; nothing downstream can
accidentally see the future. Proof Mode additionally carries its own formal runtime assertion
that raises an error and refuses to serve a replay if the window it's about to show could contain
any information from after the issue time.

WEATHER FORECAST & BIAS CORRECTION: We don't get to use the actual observed temperature for the
target time -- that would be leakage, since we don't have tomorrow's real weather today. Instead
we use a day-ahead weather FORECAST, and because forecast weather is systematically biased
(too hot, too cold, depending on time of day), we apply an adaptive bias correction: for each
15-minute time-of-day slot, we look at the last 30 days of forecast-vs-observed error --
computed using only data at least 24 hours old, same leakage constraint -- and use that rolling
average error to correct today's forecast temperature before it goes into the model.

MODEL: We use ordinary least squares (OLS) on standardized features, not a more complex model
like XGBoost. That wasn't the default choice -- we ran a head-to-head experiment (see
phase2_final_report.txt): OLS beat XGBoost on this dataset on every metric that matters here --
overall MAPE (6.33% vs 6.57% at that stage of the pipeline), peak-day MAPE (7.47% vs 8.43%), and
daily-peak-timestamp MAPE (5.76% vs 6.21%). Given that XGBoost was not more accurate, we kept
OLS for its transparency, its ~4.5-second fit time, and the fact that every prediction can be
traced back to an explicit linear combination of named features -- important when you're also
trying to audit the pipeline for leakage, which we found and fixed a version of during Phase 13
(a growth-term reference-window inconsistency between two application paths, now unified into
one canonical scoring function).

UNCERTAINTY & RELIABILITY: Alongside the point forecast (P50), we fit P10/P90 quantile
regression via IRLS on out-of-fold residuals, with reliability-aware widening -- a
lower-reliability forecast gets a wider band, not a falsely confident one. Reliability itself is
HIGH/MEDIUM/LOW based on how much of the input data for that forecast had to be reconstructed.

RISK & LOCALIZATION: A single Grid Stress Score combines utilization (P50 and P90 against a
capacity assumption), day-over-day growth, heat, and reliability into one number and a
NORMAL/WATCH/HIGH/CRITICAL level; a separate rule maps utilization and reliability to a
LOW/MODERATE/HIGH/CRITICAL peak-risk label. DISCOM-level numbers are MODELED ESTIMATES --
Delhi-wide demand split by disclosed allocation ratios, never live feeder telemetry, and clearly
labeled as such everywhere they appear.

SCENARIO ENGINE & RECOMMENDATIONS: The What-If tab genuinely recomputes the forecast through the
same fitted model for a perturbed temperature input -- it's not a lookup table. Solar is kept
separate: a disclosed, non-fitted half-sine daylight assumption subtracted from the gross
forecast, so it can never affect an after-dark peak. A deterministic rule engine (no LLM) then
turns risk, reliability, and DISCOM-level signals into plain-language advisories."

9. JUDGE Q&A (18 likely questions)
============================================================================================
1) Why OLS instead of XGBoost?
   Simple: we tested both head-to-head and OLS was at least as accurate while being far more
   transparent and auditable.
   Technical: Phase 2's controlled experiment (phase2_final_report.txt) showed OLS beating
   XGBoost on overall MAPE (6.33% vs 6.57%), peak-day MAPE (7.47% vs 8.43%), and daily-peak-
   timestamp MAPE (5.76% vs 6.21%) at that stage of the pipeline. With no accuracy advantage for
   the more complex model, OLS was kept for its transparency, ~4.5s fit time, and ease of
   auditing for leakage.

2) How do you prevent data leakage?
   Simple: the model is only ever allowed to see information from 24+ hours before the moment
   it's predicting.
   Technical: every lag/rolling feature is built with an explicit shift(H) or greater at the
   single point the whole feature matrix is constructed, so leakage-safety is structural, not a
   per-function check. Proof Mode additionally carries a runtime assertion that raises an error
   rather than serve a replay window that could contain post-issue-time information.

3) Where does "tomorrow's weather" come from?
   Simple: a day-ahead weather forecast file, not the real observed weather for that day.
   Technical: delhi_weather_forecast_day1.csv, resampled to 15-minute resolution and used as
   temp_fcst_C; the model never sees temp_C (observed) for the target block.

4) How is the weather forecast bias-corrected?
   Simple: we track how wrong the weather forecast has recently been, at each time of day, and
   nudge today's forecast by that same recent error.
   Technical: for each 15-minute time-of-day slot, a 30-day rolling mean of (observed - forecast)
   error, itself lagged by 24h so it uses only past data, is added to the raw forecast
   temperature to produce temp_corr, the value actually fed to the model.

5) How is missing load data handled?
   Simple: gaps are filled from the closest earlier day that actually has real data for that
   time of day, not a fixed "same time yesterday" rule -- and every filled block is flagged.
   Technical: nearest-observed-day imputation, replacing an earlier same-time-yesterday
   approach; the improvement was measured at 6.01%->5.94% full-test-period MAPE. Every imputed
   block sets lag24_imputed/lag48_imputed flags that directly drive the reliability score.

6) Why should I trust this forecast?
   Simple: because it tells you when NOT to fully trust it -- via the reliability badge -- rather
   than presenting every forecast with false confidence.
   Technical: reliability is HIGH/MEDIUM/LOW based on how much of a forecast's input data was
   reconstructed, and directly widens the P10/P90 band and shifts the peak-risk/advisory logic
   when it's degraded.

7) What does P90 actually mean here?
   Simple: a value we expect the real demand to stay below about 90% of the time.
   Technical: the upper quantile from IRLS quantile regression on out-of-fold residuals, with
   reliability-aware multiplicative widening; empirically, actual demand fell at or below P90 in
   86.6% of the 5,817 test blocks (close to, slightly under, the nominal 90% target).

8) Why does the stress score use both P50 and P90, not just P50?
   Simple: P50 alone can look comfortable while the uncertain upper end is not -- we want to
   catch that.
   Technical: the score explicitly checks for exactly that pattern (util50 < 0.88 <= util90) and
   fires a dedicated PREPARE advisory when it occurs -- which is in fact the real state on the
   demo day, 2025-06-12 (P50 87% of capacity, P90 94%).

9) Where do the DISCOM numbers come from?
   Simple: Delhi-wide demand split into shares for BRPL, BYPL, TPDDL, and a residual bucket,
   using disclosed allocation ratios -- not separate per-utility forecasts.
   Technical: discom_estimate() applies fixed, disclosed RATIO values to the Delhi-wide P50/P90;
   this is why the dashboard labels these figures "MODELED ESTIMATE" everywhere they appear.

10) Is the DISCOM data real?
    No -- it is a modeled allocation of the real, measured Delhi-wide demand, not independently
    measured or reported per-DISCOM data. This is disclosed on every screen that shows it.

11) Why is there no feeder-level telemetry?
    Because this project's real, measured input is city-wide 15-minute load data -- feeder-level
    telemetry was never part of the available dataset, so the system is honest that DISCOM
    numbers are modeled, not measured, rather than presenting an unsupported level of detail.

12) How does the What-If simulator actually work?
    Simple: the temperature slider genuinely re-runs the real forecast model with a shifted
    temperature input; the solar slider is a separate, disclosed assumption subtracted
    afterward.
    Technical: apply_temp_delta() perturbs only the corrected-forecast temperature feature (and
    features derived from it) and re-fires the same fitted OLS/quantile pipeline; solar_profile_
    mw() is a non-fitted half-sine daylight-hours assumption, never blended into the model
    itself.

13) Is the solar output a genuine model prediction?
    No -- it's explicitly disclosed, assumption-based scenario arithmetic (a half-sine daylight
    curve), not fitted from any data in this project, and the dashboard labels it as such.

14) Can this system control the grid?
    No. It is a forecasting and decision-support dashboard only -- it has no control or write
    access to any grid, DISCOM, or SLDC system; it only displays estimates and advisories.

15) How did Proof Mode work for the demo event?
    A forecast for 12 June 2025's actual peak was issued using only information available at
    2025-06-11 23:00 (24 hours before), predicting 7,795.2 MW; the real outcome, 8,392.6 MW, was
    revealed only afterward, separately, with nothing recomputed with hindsight.

16) What happens when the model is wrong?
    It's shown honestly, not hidden or silently corrected. The Proof Mode primary event is
    itself an example: a real 597.4 MW / 7.1% underforecast that still fell inside, but very
    close to the edge of, the P10-P90 band (25 MW margin) -- disclosed on-screen as a genuine
    near-miss.

17) What's the biggest limitation of this system?
    The forecast quality is bounded by real, disclosed data-completeness gaps in the underlying
    telemetry (some 15-minute blocks have to be reconstructed from a nearby day), and the system
    has never been tested against a real HIGH/CRITICAL-risk day -- no such day occurred in the
    test period, so that state has only been exercised via the labeled +5 degC What-If scenario.

18) What would a real DISCOM deployment path look like?
    Replacing the modeled DISCOM allocation with real per-feeder or per-DISCOM telemetry where
    available, validating the Grid Stress Score and advisory thresholds against real operator
    decisions and outcomes over a full season (including at least one real HIGH/CRITICAL day),
    and formal review by DISCOM/SLDC domain experts before any operational use -- none of which
    has happened yet; this system is a decision-support prototype, not an operationally-
    validated deployment.

10. FAILURE PLAN (top 5, Failure -> Detection -> Fallback)
============================================================================================
1) FAILURE: Judging-room internet is unavailable or unstable.
   DETECTION: Not applicable to this app's own function -- grep-verified and load-tested with
   the OS network layer hard-blocked: 0 exceptions across every tab and interaction. The only
   real (non-blocking) outbound attempt was Streamlit's own anonymous usage-stats ping, now
   disabled via .streamlit/config.toml.
   FALLBACK: None needed for the app itself. Launch it before walking into the room if possible,
   simply as good practice, not because it needs the network to start.

2) FAILURE: The three source CSVs are missing, moved, or corrupted at the expected data path.
   DETECTION: build_backend() explicitly checks for all three required files and raises a
   BackendError naming exactly which are missing; safe_backend() catches this before the UI
   renders.
   FALLBACK: st.error() shows the exact missing-file message and the app stops cleanly -- no
   traceback. Presenter fallback: keep a second copy of the data folder (USB drive / second
   laptop) and confirm the data path before the demo starts.

3) FAILURE: A future code change (or an unanticipated interaction sequence) reintroduces a
   dashboard-state / widget error, of the same class as the reveal-toggle bug found this phase.
   DETECTION: main() wraps each of the three tabs' render calls in its own try/except; any
   uncaught exception is caught per-tab.
   FALLBACK: The affected tab shows a plain "Something went wrong" message with the real
   traceback hidden behind a collapsed "Technical details" expander -- never inline, never
   crashing the whole app. Presenter fallback: switch to a different tab, or reselect the same
   day/event to force a clean rerun; worst case, refresh the browser tab (the model is still
   cached in-process, so this recovers in under a second).

4) FAILURE: A slider is pushed to an edge case (extreme temperature, solar at the exact
   sunrise/sunset boundary) and produces an unexpected combination.
   DETECTION: apply_temp_delta() explicitly clips to the hard temperature bounds and reports how
   many blocks were clipped via scn["notes"], shown as an inline st.warning(); solar_profile_mw()
   is structurally zero outside daylight hours by construction, not by a runtime check that could
   be bypassed.
   FALLBACK: Any clipping or edge condition is shown to the presenter inline, not hidden; reset
   the slider to 0 / disable solar to return to the known-good BASE state.

5) FAILURE: The presenter is asked to demo a real HIGH/CRITICAL-risk day, but no such day exists
   in the real test period.
   DETECTION: This is a demo-content risk, not a code risk -- confirmed this phase that the real
   peak_risk distribution across all 61 test days is 54 LOW / 7 MODERATE / 0 HIGH / 0 CRITICAL.
   FALLBACK: Use the +5 degC What-If scenario on 2025-06-12 (Section 4), always clearly labeled
   as a hypothetical scenario, never claimed as a historical event -- this is the only state
   anywhere in the system, real or scenario, that reaches HIGH.
